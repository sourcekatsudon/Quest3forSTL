# Supabase backend (opt-in until production cutover)

The existing Blob backend remains available for rollback and later recovery. Selecting Supabase does not read or delete Blob data. This is a new, initially empty catalog; do not interpret it as proof of old data loss.

## Setup
1. Use a dedicated Supabase project. Do not share another application's project without explicit approval.
2. In its SQL editor, execute server/supabase-schema.sql. It creates two RLS-enabled tables and SECURITY INVOKER RPCs with explicit service_role grants only. Check that Data API is enabled.
3. In Storage, create a PRIVATE bucket named stl-room-assets, with a file size limit of 50 MiB (or the lower limit allowed by the plan; align STL_MAX_FILE_BYTES). Do not add public/anon/authenticated read or write policies. Do not modify the storage schema directly.
4. Set server-only Vercel environment variables: STL_STORAGE_BACKEND=supabase, SUPABASE_URL=https://<project-ref>.supabase.co, SUPABASE_SERVICE_ROLE_KEY=<legacy server service_role JWT>, and optionally SUPABASE_STORAGE_BUCKET=stl-room-assets. Never prefix the key with VITE_. The old BLOB_READ_WRITE_TOKEN is not required in Supabase mode. Use preview variables first; do not expose the key in logs.
5. Verify npm ci, npm run typecheck, npm test, npm run build. In a separate preview project verify upload of real STL/STEP/GLB, thumbnail, original SHA256, optimized display, refresh on PC/Quest, photo capture, concurrent uploads, invalid input, deletion, and failure behavior. Check 6MB+ and the chosen maximum upload size; the implementation uses standard signed PUT, not resumable TUS. For large files a failed transfer must be restarted. See https://supabase.com/docs/guides/storage/uploads/standard-uploads.
6. Only after preview verification and authorization set the production variables and deploy. To roll back set STL_STORAGE_BACKEND=blob and restore the previous Blob connection; this does not merge the two catalogs. A quota-suspended Blob store may still be inaccessible.

## Data and limits
The database reserves slots before signing URLs (125-minute reservation, signed URLs currently valid for two hours), publishes only validated bytes and serializes reservations per kind. Each model has a distinct UUID and immutable paths; deletion tombstones the model before removing its assets. Global per-IP write rate limit is 30 per minute. Existing anonymous shared-library semantics remain: anyone who can access the application can read/add/delete models. Private storage and signed URLs prevent arbitrary direct bucket access, not abuse through the public application. Restrict application access if needed.

Model and photo lists query the database, not Storage listing. Assets use short-lived signed redirects. Server validation and STEP conversion still read originals and write derived assets. Supabase quotas and inactivity suspension still apply. Signed upload URLs do not constrain the exact byte size or MIME type individually: the bucket cap bounds uploads and commit validates bytes. Monitor uncommitted reservations and Storage usage. Expired reservations and unreferenced objects require administrative cleanup; never remove a published model's assets. Use the Storage API to remove only verified orphan objects. The app does not automatically migrate old Blob data. Retain the old store, and plan a verified copy preserving IDs, paths, manifests and dates once it becomes accessible.
